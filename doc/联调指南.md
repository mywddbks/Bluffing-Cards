# 唬牌联调指南

本文面向负责 C++ 后端的同学：从启动前端、实现 REST/WS，到完整走通一局联机牌局。

契约以 [`doc/api.md`](api.md) 为准；规则以 [`doc/游戏规则.md`](游戏规则.md) 为准。

## 1. 先跑通前端

```bash
node tools/serve.mjs
# http://localhost:8080
```

此时“快速人机”完全可用，不需要后端；“创建联机房间/加入房间”会请求 `/api/rooms`，在后端未启动时会报错。

## 2. 选择部署方式

### 同源（推荐）

把 `static/` 作为 C++ 服务的静态目录，REST 挂在 `/api/*`，WebSocket 挂在 `/ws`。前端无需修改配置。

### 分端口

页面先设置全局配置，再加载 `main.js`：

```html
<script>
  window.__BLUFF_CONFIG__ = {
    apiBase: "http://127.0.0.1:9000",
    wsPath: "/ws"
  };
</script>
```

- 后端需要允许跨域（CORS）：至少 `GET, POST, OPTIONS`，`Content-Type` 请求头。
- WebSocket 不受浏览器 CORS 头限制，但后端应校验 `Origin`（可选）。
- `wsPath` 可以是 `/ws`，前端会自动追加 `?room=&token=&v=1`。

## 3. 最小联调顺序

1. 实现 `GET /api/health`，浏览器访问确认 JSON。
2. 实现 `POST /api/rooms`，用 curl 建房，确认返回 `roomCode/playerId/playerToken/wsPath/room`。
3. 实现 `GET /api/rooms/{code}`，确认房间摘要。
4. 实现 WebSocket 握手和首帧 `state`（`phase:"waiting"`），前端应进入等待房间。
5. 实现 `POST /api/rooms/{code}/join`，让第二个浏览器加入；两个页面都应看到座位变化。
6. 实现 `ready`、`start`、`addAI`、`removeAI`，前端大厅按钮应生效。
7. 实现 `start` 后的发牌与 `GameView`，前端应进入牌桌；先手应能选择牌面并出牌。
8. 逐个实现 `play`/`challenge`/`pass`，每步都检查所有人视图是否脱敏。
9. 实现结算、`rematch`、`leave`。
10. 用两个浏览器 + 一个 AI 座位跑完 2 人局和 3 人局。

## 4. REST 自测

```bash
curl -s http://localhost:9000/api/health
curl -s -X POST http://localhost:9000/api/rooms \
  -H "Content-Type: application/json" \
  -d '{"maxPlayers":3,"nickname":"张三"}'
curl -s http://localhost:9000/api/rooms/7K2M9Q
curl -s -X POST http://localhost:9000/api/rooms/7K2M9Q/join \
  -H "Content-Type: application/json" \
  -d '{"nickname":"李四"}'
```

错误响应必须是：

```json
{ "error": { "code": "ROOM_FULL", "message": "房间已满" } }
```

## 5. WebSocket 自测

浏览器控制台（先建房/加入拿到 session）或任意 WebSocket 客户端：

```text
ws://localhost:9000/ws?room=7K2M9Q&token=...&v=1
```

发送：

```json
{"v":1,"type":"ready","actionId":"test-1","baseSeq":0,"payload":{"ready":true}}
```

服务端应先回 `state`（或对非法准备回 `error`）。注意：

- 首帧必须是 `state`；前端在收到首帧前一直显示“连接中”。
- `state.seq` 必须递增；前端下一次动作的 `baseSeq` 会自动使用最新 seq。
- 每个玩家收到的 `view` 必须个性化；不要为了省事把内部 `state` 直接发出去。

## 6. 前端联调观察点

打开浏览器 DevTools：

- **Network → WS**：看动作信封是否有 `v/type/actionId/baseSeq/payload`；看 `state.seq` 是否递增。
- **Console**：前端在协议版本不一致、未捕获异常时会打印/提示；联调时保持 Console 打开。
- **Application → Local Storage**：`bluff.session.v1` 保存 `roomCode/playerId/playerToken`；`bluff.nickname.v1` 保存昵称。
- **Elements**：手牌应只有自己的牌；翻开揭牌弹窗后才出现被查组。
- 刷新页面不会自动重连（当前版本设计），需要重新加入。

## 7. 关键校验不要漏

- 宣称数量必须等于实际出牌张数；宣称牌面必须是 A～K。
- 跟牌只能使用本轮锁定牌面；先手第一手才可选牌面。
- 先手不能过牌/揭牌；揭牌只能查最后出牌组且不能查自己。
- 揭牌时大小王永远算真；收牌者收走整轮牌堆。
- 收牌者的下一位 active 领出；无揭牌结束时最后出牌者的下一位 active 领出。
- 出完最后一张只是 pending；本轮结算仍为 0 才锁名；被揭牌收牌则回 active。
- 2 人局第 1 名锁定即结束；3 人局第 2 名锁定后结束。
- `reveal` 事件只带被查最后一组；`play`/`challenge`/`collect` 不带牌。
- `players[].hand` 永远不存在。

## 8. 常见问题

### 前端一直显示“连接中”

- WebSocket 地址/路径不对；检查 `wsPath` 和实际挂载点。
- 握手后没有立即发送 `state`；前端在等首帧。
- 后端在升级前就拒绝了 token/房间；检查关闭码 4401/4402/4403。

### 每次操作都提示“状态已过期”

- 服务端 `seq` 没有递增，或前端/后端用了不同的 seq 概念。
- `state.seq` 应为房间级单调递增；动作失败不应消耗 seq（建议）。

### 揭牌后前端没有弹窗

- `events` 中没有 `reveal`，或事件 `type` 拼写错误。
- `reveal.cards` 缺失；前端只从该事件读取牌面。
- `state.payload.events` 必须是数组。

### 其他玩家能看到我的手牌

检查是否把内部 `GameState` 直接序列化为 `view`；`getView` 必须按玩家生成，并只给 `you.hand`。

### 刷新后无法恢复

当前前端不自动重连；这是范围约定。后端可以保留 token 和 `sync`，但前端 UI 尚未实现自动恢复。

### 移动端按钮被挤出屏幕

前端已用 `minmax(0,1fr)`、`min-width:0` 和断点修复；如果新增按钮，保持网格子项可收缩。

## 9. 验收脚本建议

后端至少跑通：

1. 3 人房：建房 → 加入 2 人 → 准备 → 开始 → 发 18 张。
2. 2 人房：27 张，先手选牌面，出牌，跟牌，过牌两轮，结算。
3. 揭牌：真话（含王）和假话各一次，确认收牌者与下一轮领出。
4. pending：某人出完最后一张，本轮结算锁名；2P 结束/3P 继续。
5. 3P 连续锁名，最终名次正确。
6. 同一动作重发两次，确认 actionId 幂等。
7. 用两个浏览器同时观察：对方手牌不可见；揭牌弹窗只显示被查组。
8. 断线/关闭页签：其他玩家看到离线/离开；等待房间可重新加入。

## 10. 与本地 mock 的差异

本地 mock 直接开局（无大厅）、`rematch` 立即重开；联机版有等待房间、准备、房主开始，`rematch` 回等待房间。两者共用同一套 UI 和规则，但联机结果以服务端为准。
