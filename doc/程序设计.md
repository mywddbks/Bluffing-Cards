# 唬牌程序设计

## 1. 项目概述

本项目实现一款 2～3 人、54 张牌的“唬牌”（Bluff / Cheat / 吹牛）游戏。玩家轮流扣牌并宣称“若干张某个点数”，下家可以跟牌、揭牌质疑或过牌；先出完手牌并锁定名次者获胜。游戏的核心是不完全信息下的心理博弈。

课程分工：

- 陈昱景：前端
- 李子昂：后端
- 曾沛然：人机
- 张云航：报告

本仓库当前交付**前端**：可直接运行的人机版、联机客户端、规则参考实现、完整接口文档和测试。C++ 后端与正式人机 AI 由对应成员实现。

## 2. 总体架构

```text
┌───────────────────────────── 浏览器 ─────────────────────────────┐
│ static/index.html                                                │
│   ├─ css/*             设计系统与牌面                              │
│   └─ js/main.js        应用装配                                   │
│        ├─ ui/*         首页/大厅/牌桌/结算/弹窗                     │
│        ├─ game/mock/*  本地规则引擎 + 演示机器人 + MockClient       │
│        └─ net/*        REST + WebSocket + 协议信封                 │
└───────────────┬──────────────────────────────┬───────────────────┘
                │ REST /api/*                  │ WebSocket /ws
                ▼                              ▼
        ┌──────────────────────────────────────────────┐
        │ C++ 后端（课程组实现）                         │
        │ 房间管理 / 发牌 / 裁判 / 服务端权威视图 / AI 调度 │
        └──────────────────────────────────────────────┘
```

- **前端不判胜负**：联机时只渲染服务端下发的 `GameView`。
- **本地 mock 是规则参考实现**：在无后端时提供完整可玩的人机体验，也用于前端单测。
- **协议与实现解耦**：`NetworkClient` 与 `MockClient` 暴露相同接口，UI 不区分数据来源。

### 3.1 状态流

```text
动作点击
  → UI 生成 {type,payload}
  → client.send()
  → mock: engine.applyAction() / network: WebSocket
  → onState({view,events})
  → main.handleState()
  → phase=waiting → 大厅；playing → 牌桌；finished → 结算
  → UI 全量重绘；临时选牌状态保留在 table 模块
```

### 3.2 关键界面状态

- 首页：昵称、快速人机、联机入口、规则/设置。
- 大厅：座位、房主、AI、准备、开始。
- 牌桌：对手、中央宣称/牌堆/最后出牌、最终确认、手牌、牌面选择、操作栏、历史。
- 揭牌：只展示被查组。
- 结算：领奖台、再来一局、返回。

## 4. 规则引擎设计

`static/js/game/mock/engine.js` 是纯函数实现，不访问 DOM、网络或时间（时间仅用于事件戳），随机种子可注入。

### 4.1 数据结构

- `state.players[]`：内部含 `hand`；`getView` 会脱敏。
- `state.round`：`claimRank`、`lastPlay`（内部含 cards）、`pile`、`passCounts`、`emptyOrder`、`stage`。
- `state.history`：最近 200 条事件。
- `state.seq`：每次成功动作 +1，供联机协议参考。

### 4.2 核心算法

1. **发牌**：洗牌后按座位轮流发，2 人各 27，3 人各 18。
2. **行动权**：只允许 active 玩家行动；`nextActive` 顺时针跳过 pending/locked。
3. **出牌**：校验牌在手中、数量与宣称一致、牌面锁定；更新最后出牌组；清零过牌；手牌为 0 时转 pending。
4. **揭牌**：检查最后组每张牌是否等于宣称牌面或王；真话质疑者收牌，假话被质疑者收牌；收牌者下一位 active 领出。
5. **过牌**：第一次过牌后若所有 active 都过牌，进入 `finalConfirm`；第二次过牌后若所有 active 都完成，弃牌结束本轮；任何出牌/揭牌重置。
6. **锁名**：本轮结束时，pending 且手牌为 0 的玩家按出完顺序锁名；2 人局锁 1 人结束，3 人局锁 2 人结束。
7. **下一轮**：收牌者下一位 active，或最后出牌者下一位 active；无人 active 时兜底结算。

### 4.3 信息隐藏

`getView(state, playerId)` 只输出：

- 公开玩家信息（座位、昵称、剩余张数、状态、名次、过牌数、是否轮到）；
- 自己的手牌；
- 本轮公开信息（宣称牌面、牌堆数量、最后出牌者、最后组数量/宣称，不含实际牌）；
- 历史事件；只有 `reveal` 事件带被查组 cards。

内部 `lastPlay.cards`、`pile`、其他人的 `hand`、随机种子永不进入视图。该约束有单测覆盖。

## 5. 演示机器人

`game/mock/bots.js` 仅接收自己的 `GameView` 和随机源，不读取其他玩家手牌，也不调用内部 state。

策略：

- 先计算可出的“真牌”（等于当前牌面或王）；优先出真牌；手牌少或处于最终确认时更保守。
- 偶尔混入非牌面牌进行 bluff；性格 `steady` 更少诈，`bluffer` 更激进，`balanced` 居中。
- 是否揭牌基于最后组数量、目标性格、自己手牌数、是否最终确认；手牌很多时更倾向质疑。
- 所有动作必须落在 `view.you.actions` 允许范围内；非法则回退到过牌/合法出牌。

**边界**：这是前端演示 Bot，不是课程要求的正式 AI；正式 AI 应由后端实现，并可复用同样的公开信息约束。

## 6. 联机协议设计

- REST：`/api/health`、`POST /api/rooms`、`GET /api/rooms/{code}`、`POST /api/rooms/{code}/join`。
- WebSocket：`/ws?room=&token=&v=1`。
- 客户端动作：`ready/start/addAI/removeAI/play/challenge/pass/rematch/leave/sync/ping`。
- 信封：`{v,type,actionId,baseSeq,payload}`；`actionId` 幂等，`baseSeq` 防止过期动作。
- 服务端：`state`（个性化 `GameView` + 新事件）、`error`、`pong`。
- 视图脱敏、序号、错误码、事件字段详见 [`api.md`](api.md)。

## 7. 测试与质量

- Node 原生 `node:test`，无第三方依赖；覆盖牌组、规则引擎、机器人合法性、协议信封、网络客户端、JSON 示例。
- 浏览器验证：首页、2P/3P 人机、选牌/确认、揭牌、结算、历史、规则、设置、移动端；Chrome headless 截图存于 `doc/images/`。
- 关键不变量：视图不泄露手牌；机器人不偷看；服务端/引擎是唯一裁判；非法动作不改变状态。
